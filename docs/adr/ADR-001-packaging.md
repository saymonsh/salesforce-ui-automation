# ADR-001: אריזת האפליקציה כתוכנה מותקנת ל-Windows (ללא Python מותקן מראש)

**Status:** Accepted
**Date:** 24.06.2026
**Deciders:** סיימון (בעל הפרויקט)
**Supersedes:** —

---

## TL;DR

עוברים מהרצה משורת הפקודה (`python -m src.main` עם `venv` + `pip`) ל**מתקין יחיד** שהמשתמש מריץ בדאבל-קליק, **בלי Python מותקן מראש ובלי הקפצת UAC**.

- **אריזה:** PyInstaller במצב `onedir` (תיקיה עם EXE + runtime מלא).
- **התקנה:** מתקין Inno Setup **per-user** (לתיקיית המשתמש), כך ש-UAC לא קופץ.
- **קבצים ניתנים-לכתיבה:** `config.ini`, `draft.json`, לוגים — עוברים ל-`%APPDATA%\WelfareSFAutomation\`.
- **חתימה דיגיטלית:** לא בשלב ראשון (נשאר מסך SmartScreen חד-פעמי). אפשר להוסיף בהמשך.
- **עדכונים:** ידני — החלפת מתקין.
- **Chrome:** נשאר תלות חיצונית, **לא** נארז.

---

## Context

### המצב היום

האפליקציה היא פרויקט פיתוח, לא תוצר מופץ. כדי להריץ אותה צריך:

```powershell
python -m venv .venv
.\.venv\Scripts\activate
pip install -r requirements.txt
python -m src.main
```

זה דורש מהמשתמש להתקין Python, ליצור סביבה וירטואלית, להתקין תלויות ולהריץ משורת פקודה. קהל היעד הוא **אופרטור במשרד הרווחה**, לא מפתח — עבורו זה מחסום בלתי-עביר.

### המטרה

המשתמש מקבל **מתקין אחד**, מריץ אותו, ומקבל אפליקציית דסקטופ עם אייקון וקיצור בתפריט התחל — בלי Python, בלי טרמינל, בלי שלבי התקנה ידניים. חוויית התקנה כמו של Chrome או Claude Desktop.

### כוחות פועלים (Forces)

1. **שילוב CPython + Selenium + שכבת Win32 (`ctypes`).**
   האפליקציה משלבת CPython "אמיתי" עם הטמעת חלון Chrome אמיתי דרך HWND (issue #19, ראה `win_window.py`). כל מנגנון אריזה **חייב לשמר את ה-runtime הזה אחד-לאחד**, אחרת ההטמעה ותתי-תהליכי Selenium נשברים. זה פוסל פתרונות שעוטפים את Python בצורה לא-סטנדרטית.

2. **תלות חיצונית ב-Chrome.**
   Selenium נוהג בכרום **המותקן על המכונה** (פותח, לוחץ, מקליד ב-Salesforce). האפליקציה אינה מציירת דפדפן בעצמה. אנחנו לא אורזים דפדפן.

3. **chromedriver מגיע בזמן ריצה.**
   נפתר אוטומטית ע"י **Selenium Manager** (מובנה ב-Selenium 4.6+), שמוריד build תואם ל-Chrome המותקן. ההורדה הראשונה דורשת אגרס ישיר (`setup_proxy()` מסיר משתני proxy). זה ממשיך לעבוד גם מתוך EXE.

4. **`config.ini` ו-`draft.json` נכתבים בזמן ריצה — וזה הסיכון האמיתי.**
   - `config.ini` חובה ליד ההפעלה; `config_instance = Config()` נבנה **בזמן import** (`src/core/config.py:98`), ו-`main()` מציג שגיאה ב-`MessageBoxW` אם הוא חסר/לא תקין.
   - `draft.json` נכתב בזמן ריצה ע"י הגריד (issue #18).
   - אחרי התקנה ל-`Program Files` (קריא-בלבד) — כתיבה לשם תיכשל.
   **זה השינוי הארכיטקטוני האמיתי**, לא האריזה עצמה.

5. **קהל ממשלתי.**
   - **UAC** (בקשת הרשאת מנהל) — אסור בהחלט (דרישה מפורשת של בעל הפרויקט).
   - **SmartScreen** ("Windows protected your PC") — מקובל בשלב ראשון, ניתן לבטל בהמשך עם חתימה.
   - לפעמים מנהל רשת חוסם תוכנות לא-חתומות לגמרי.

---

## Decision

לארוז עם **PyInstaller במצב `onedir`** ולעטוף ב**מתקין Inno Setup per-user**. במקביל, **להעביר את כל הקבצים הניתנים-לכתיבה ל-`%APPDATA%\WelfareSFAutomation\`** עם זריעה אוטומטית בהפעלה ראשונה.

Chrome נשאר תלות חיצונית; chromedriver ממשיך להגיע דרך Selenium Manager בזמן ריצה.

---

## Options Considered

### Option A: PyInstaller `onedir` + Inno Setup installer  ← **נבחר**

| ממד | הערכה |
|------|--------|
| מורכבות | בינונית — spec file + סקריפט Inno + רילוקיישן נתיבי קבצים |
| עלות | אפס (כלים חינמיים), מלבד חתימה אופציונלית |
| התאמה ל-runtime | מושלמת — אותו CPython, ה-Win32 וההטמעה עובדים זהה |
| התנעה | מהירה — אין פרישה מחדש בכל הרצה |

**Pros:** בדיוק "installer שפורש קבצים כמו כרום". התנעה מהירה. ידידותי לאנטי-וירוס (קבצים על הדיסק, לא self-extract). קל לצרף `config.ini.example` ונכסים. הסרה נקייה. תומך טבעית בהתקנת per-user (ללא UAC).
**Cons:** התוצר הוא תיקיה ולא EXE בודד (אך המשתמש רואה רק את המתקין — שקוף לו). דורש שני כלים (PyInstaller + Inno).

### Option B: PyInstaller `onefile` (EXE בודד)

| ממד | הערכה |
|------|--------|
| מורכבות | נמוכה-בינונית |
| התנעה | **איטית** — פורש את כל ה-runtime ל-`%TEMP%` בכל הרצה |
| אנטי-וירוס | **בעייתי** — self-extract מסומן כחשוד לעיתים קרובות |

**Pros:** קובץ יחיד באמת.
**Cons:** מאחר שבעל הפרויקט מוכן למתקין, היתרון היחיד מתבטל. התנעה איטית, יותר false-positives של AV, ו-`_MEIPASS` קריא-בלבד מקשה על קבצי נתונים. **פחות מתאים אחרי ההבהרה שמתקין מקובל.**

### Option C: `flet build windows` (בנייה נייטיב מבוססת Flutter)

| ממד | הערכה |
|------|--------|
| מורכבות | **גבוהה / לא ודאית** |
| סיכון ל-runtime | גבוה — עוטף את Python אחרת; הטמעת ה-HWND ותתי-תהליכי Selenium לא מובטחים |

**Pros:** התוצר הכי "נייטיב".
**Cons:** המנוע החדש של Flet משנה את אופן אירוח Python. שכבת ה-Win32 (issue #19) ותהליכי Selenium הם בדיוק סוג הדברים שנשברים שם. סיכון גבוה מדי לתמורה נמוכה.

---

## Trade-off Analysis

המתח המרכזי הוא **שליטה ב-runtime מול "נייטיביות"**. Option C נראה הכי מקצועי אבל מסכן את שתי הליבות הכי שבריריות: הטמעת Chrome (HWND owned-overlay) ותהליכי Selenium. Options A/B שומרים על CPython בדיוק כמו שהוא רץ היום — אם זה עובד ב-`python -m src.main`, זה יעבוד באריזה. מאחר שמתקין מקובל, **A גובר על B** בכל ממד מלבד "קובץ בודד", שכבר לא נדרש.

---

## דרישת ה-UAC — איך מבטיחים שלא יקפוץ

UAC קופץ **רק** כשכותבים למיקום מוגן (`Program Files`, `HKLM`). התקנה **per-user** לתיקיית המשתמש לא דורשת elevation. זו בדיוק התבנית של Chrome (per-user) ושל מתקיני Squirrel (כמו Claude Desktop).

הגדרות Inno Setup הנדרשות:

| הגדרה | ערך | למה |
|--------|------|------|
| `PrivilegesRequired` | `lowest` | המתקין רץ כמשתמש רגיל, ללא בקשת elevation |
| `DefaultDirName` | `{localappdata}\WelfareSFAutomation` | כתיבה ל-`%LOCALAPPDATA%` — אזור מורשה, אין UAC |
| קיצורים | `{userprograms}` / `{userdesktop}` | תפריט התחל ושולחן עבודה של המשתמש, לא של כל המכונה |
| Registry (אם בכלל) | `HKCU` בלבד | `HKLM` מצריך מנהל; `HKCU` לא |

**טרייד-אוף יחיד:** התקנה per-user = האפליקציה מותקנת לפרופיל המשתמש הנוכחי בלבד. אם שני משתמשי Windows שונים על אותה מכונה צריכים אותה — כל אחד מתקין לעצמו. בקהל היעד (אופרטור = משתמש יחיד למכונה) זה לא בעיה. התקנת all-users הייתה *מחייבת* UAC — הדרישה מכריעה לטובת per-user.

---

## UAC מול SmartScreen — שני חלונות שונים

קל לבלבל ביניהם; הם נפרדים לחלוטין:

| החלון | מתי קופץ | איך מבטלים | עלות |
|-------|----------|------------|------|
| **UAC** ("לאפשר לאפליקציה לבצע שינויים?") | התקנה למיקום מוגן | התקנה per-user (ההחלטה לעיל) | אפס |
| **SmartScreen** ("Windows protected your PC") | קובץ לא-חתום | חתימה דיגיטלית בלבד | ~200–500 ש"ח/שנה |

המשמעות: ההחלטה על per-user מבטלת את UAC ללא עלות. רק חתימה מבטלת את SmartScreen. בשלב ראשון נשאר מסך SmartScreen חד-פעמי בהתקנה הראשונה בלבד — וכלום אחר כך.

## החלטות נלוות (ברירות המחדל שאושרו)

### חתימה דיגיטלית — **לא בשלב ראשון**
תעודת code-signing מבטלת את אזהרת SmartScreen ונראית מקצועית, אך עולה כסף ודורשת אימות זהות. בשלב ראשון, עם קהל מצומצם ומוכר, המשתמשים יכולים ללחוץ "Run anyway". אפשר להוסיף חתימה בהמשך אם האזהרה מפריעה או ההפצה מתרחבת. (סוג OV זול אך דורש "התחממות" מול SmartScreen; EV יקר ונקי מיידית.)

### עדכונים — **ידני**
שליחת מתקין חדש שדורס את הישן. עדכון אוטומטי דורש שרת אירוח גרסאות + קוד בדיקת עדכונים — מורכבות מיותרת לקהל קטן. ניתן להוסיף בעתיד.

### Chrome — **תלות חיצונית**
כמעט בטוח שמותקן על מכונות הארגון. אריזת Chrome for Testing הייתה מוסיפה ~150MB ואחריות לעדכוני אבטחה. אם יתברר שחסר — ייבחן אז.

## איפה יושב קובץ ה-EXE / המתקין

יש שני "איפה" נפרדים שחשוב לא לבלבל:

### א. אחסון להפצה — מאיפה המשתמש מוריד

**GitHub Releases** (מומלץ):
- כל גרסה = Release בריפו (לדוגמה `v1.0.0`), והמתקין נספח כ-**asset** (`WelfareSFAutomation-Setup-1.0.0.exe`).
- המשתמש מקבל קישור הורדה ישיר. עדכון ידני = Release חדש (מתיישר עם החלטת "עדכונים ידניים").
- **הבינארי לא נכנס להיסטוריית git** — בינארים כבדים נספחים ל-Release בלבד, לא ל-`git add`.

חלופות: Google Drive / OneDrive עם קישור, או שרת פנימי של הארגון. GitHub Releases הוא הכי נקי וחינמי.

### ב. מיקום על מחשב המשתמש אחרי התקנה

נגזר מהחלטת ה-per-user:
- **EXE ראשי + runtime:** `%LOCALAPPDATA%\WelfareSFAutomation\` (בפועל `C:\Users\<שם>\AppData\Local\WelfareSFAutomation\`).
- **קיצורים:** תפריט התחל ושולחן עבודה של המשתמש, מצביעים לשם.
- **הגדרות / דראפט / לוגים:** `%APPDATA%\WelfareSFAutomation\` (Roaming, תיקיה נפרדת מה-runtime).

## Consequences

### נהיה קל יותר
- חלוקה לאופרטורים: קובץ מתקין אחד, דאבל-קליק.
- אין תלות בסביבת פיתוח אצל המשתמש.
- אין UAC, אין טרמינל.

### נהיה קשה יותר / דורש עבודה
- **רילוקיישן קבצים (הסיכון הגדול ביותר).** צריך פונקציה מרכזית `app_data_dir()`; כל קריאה/כתיבה ל-`config.ini` / `draft.json` / לוגים עוברת דרכה. נוגע ב:
  - `src/core/config.py` — ה-singleton הנטען בזמן import. הזריקה ב-import-time חייבת למצוא קונפיג תקין ב-`%APPDATA%` או **לזרוע אחד שם בהפעלה ראשונה** מתוך `config.ini.example` הארוז, אחרת האפליקציה תקרוס מיד אחרי התקנה.
  - `src/ui/data_grid.py` — מיקום `draft.json`.
  - `src/core/logger.py` — מיקום קובצי הלוג.
- **בדיקת "מכונה נקייה".** חובה לבדוק את התוצר על Windows ללא Python כלל — אחרת מפספסים DLL חסר או תלות שלא נארזה.
- **אימות per-user ללא UAC.** לוודא על VM נקי שההתקנה רצה בלי הקפצה ושהאפליקציה כותבת קונפיג/דראפט בלי שגיאות הרשאה.

### נצטרך לחזור לבחון
- אם תידרש אפס-תלות-מוחלטת כולל Chrome — אריזת Chrome for Testing (גודל + עדכוני אבטחה).
- אם ההפצה תתרחב — חתימה דיגיטלית.
- אם עדכונים ידניים יציקו — מנגנון עדכון אוטומטי.

## Notes

- מצב `--dry_run` (ראה CLAUDE.md) ממשיך לעבוד באריזה ושימושי לבדיקת זרימת ההטמעה על מכונה נקייה ללא Salesforce.
- אילוצי הליבה הקריטיים (selectors, wait timings, מנגנון ה-stop, owned-overlay embedding) אינם מושפעים מהאריזה — אריזה לא נוגעת בהם.
